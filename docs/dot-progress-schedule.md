# Private workspace goal Gantt

The goal Gantt stays at the top of the existing authenticated WORKSPACE, with project cards below. It follows the supplied AI layout reference without importing its illustrative projects, counts or times. Fixed goal labels sit beside the time axis; dashed planned bars, solid actual intervals, known-endpoint milestones and the current Taipei time line have distinct labels. Historical details are collapsed initially.

Actual timeline records, their versions/history, project data and push counters are independent and unchanged by every schedule operation. A recorded completed interval does not itself establish that a whole goal is completed. Unknown actual starts remain null and display a known-endpoint milestone without an inferred duration. The status of a persisted plan is explicitly selected by an administrator.

## Planning interactions

The date control now supports day, Monday-start week and calendar month views in Taipei time. Previous/next controls move by the selected calendar period, clamping the selected day when moving between months of different lengths; Today returns to the current Taipei period. Week/month axes cover the full period with readable date ticks. Intervals that cross days, months or years are clipped visually without changing their stored endpoints. Known-endpoint milestones remain points, with no invented start or duration.

Week/month views are read-only overviews of independent daily boards. Each saved row shows its full owner date and offers an explicit entry to that day's editor. The complete original daily board and that day's actual groups are reloaded before editing; the overview's combined rows or actual references are never submitted as a daily save. The day view also shows overlapping plans owned by another date as read-only source links. A transient return-to-overview action restores the prior mode and anchor without writing or browser storage.

Row identity combines owner date and row ID in overviews, because IDs may repeat across daily boards. Only matching rows contribute actual-reference mapping; full source-board metadata stays available for safe day editing. Actual list/counts use unique loaded record IDs, and a referenced actual is drawn once even if multiple source-day plans reference it. Grouping explicit actual goals does not merge their intervals or establish goal completion.

Known planned bars can be moved horizontally, resized with their edge handles and reordered with a row handle. Releasing a changed gesture saves the planned board. Pointer cancellation or Escape abandons the gesture without writing. Date/time editing and row up/down controls provide keyboard and mobile alternatives. Actual bars are read only.

All mutations, sorting, Undo, archive/restore and version recovery remain scoped to the explicitly selected daily owner board. Carry rows and week/month overviews cannot be dragged into that board or reordered into its saved metadata. A proposed span that no longer overlaps its owner date, or exceeds the existing seven-day limit, is rejected rather than copied into another date. Changing date or mode cancels gestures and stale proof/results; in-flight saves prevent period navigation. Unsaved forms remain private in-memory drafts for their original date only.

An explicit short-term target can be entered as a planned goal with "No planned time" selected. It requires neither a deadline nor working hours. Distinguish numeric targets and capacity assumptions from verified production, state unknown counts as unknown, and record a planning window in the goal text only when the owner intends one. A planning window is not a delivery promise, actual work interval or completed result; loading the week/month overview never creates target rows automatically.

The administrator can explicitly add a planned goal or add the missing goal to an unscheduled actual group. Initial actual groups are a read-only derived view until that selected group is explicitly edited; loading and reordering never create plans. Ordering saves only a separate ID list, keeping every persisted row unchanged. Missing objectives are labelled rather than inferred from actions/results. Counts describe loaded actual records, and pagination does not imply complete history when more records remain.

Undo submits the previous planned rows and display order against the current schedule version with a new request ID. It creates a retained planned revision rather than erasing history. Failed saving restores the last confirmed schedule. An uncertain retry retains the exact request ID and payload. A version conflict requires an explicit reload before applying another change; no newer plan is overwritten. Session revalidation conceals and disables the private workspace, cancels gestures and confirms the role before refreshing. Logout, expiry and page departure clear private state and late responses cannot revive it. Private drafts or plans are never stored in localStorage, sessionStorage or browser history.

Cancel editing discards the current unsaved form and its pending retry without an API write; it cannot cancel an already submitted save. Opening an editor explicitly focuses and brings that form into view. Plan-time errors refer only to valid dates/times, chronological spans of at most seven days and overlap with the selected date.

An existing saved plan can be archived and restored from the collapsed archived-plans list. This toggles only its archive flag, preserving its ID, status, timestamps, actual references and display-order position. It does not cancel/archive the underlying project or actual work. Derived unsaved groups cannot be archived. Archived rows retain their actual references, so hiding a plan does not recreate its actual group as a new unsaved row; actual details remain available.

## Daily recurring objectives

In the normal day editor, an administrator can explicitly select Daily repeat, choose an included Taipei start date and optionally an included final date. Empty final date means indefinite. The rule remains a planned objective with unknown times and no actual references; it cannot manufacture a completed result, start, end or duration. Existing total objectives remain independent rows and are never rewritten to create the rule.

One source-day row stores `repeat:{frequency:"daily",from:"YYYY-MM-DD",until:null|"YYYY-MM-DD"}`. Period reads expand only dates in the selected day/week/month. Each occurrence has a stable owner-date/ID identity and original `sourceDate`/`sourceRowId`; the source-day occurrence retains its original row ID. Day and overview projections use the same identity, and the first day renders once. Future occurrences are read-only source links and never become a daily save or reorder payload. Archive/restore and Undo act on the source rule and preserve complete retained snapshots. A global maximum of 100 saved rules bounds expansion without silently truncating an overview.

No row is added by installation, deployment or reading a period. The owner adds a requested real objective through the existing authenticated UI. Current actual records, total goals, retained history and push counters remain independent. Synthetic integration and normal-browser tests assert exact preservation across reading, restart, archive and Undo.

## API contract

All endpoints use the existing administrator session, startup/rate boundaries, origin checks and no-store responses. No credential, role or security setting is added.

- GET `/api/dot-progress/schedule?date=YYYY-MM-DD` returns `{success:true,schedule:{date,version,rows,rowOrder,updatedAt}}`. An absent date board returns version 0, empty rows and an empty order.
- GET `/api/dot-progress/schedule-period?date=YYYY-MM-DD&view=day|week|month` returns `{success:true,period:{date,view,from,to,startAt,endAt},schedules}`. `from` is an included Taipei date and `to` an excluded date; `startAt`/`endAt` are the corresponding instants. Each source schedule retains its full original rows, order, version and owner date, plus read-only `matchingRowIds`. Timed plans match half-open overlap including zero-duration points; untimed plans match only when their owner date lies in the period. Source-date candidates extend seven days on either side to include carry-in/out spans, with bounded supported-calendar queries and at most 45 boards. No boards are copied, merged, rewritten or silently truncated. When rules produce dates in the period, the response additionally includes `occurrences`; this optional property is omitted for legacy boards without matching rules.
- GET `/api/dot-progress/timeline?date=YYYY-MM-DD&view=week|month&offset=0` adds optional period filtering to the existing actual journal. `view` requires `date`; omitting it preserves legacy day filtering and the existing response shape with 500-record pagination. Optional `order=newest` sorts item time (`startedAt`, or the known end when start is unknown) and ID descending; omitted order preserves legacy ascending order. Interval, point and null-start endpoint rules use the same Taipei period boundaries. Unknown modes and unsupported calendar boundaries are rejected.
- PUT `/api/dot-progress/schedule/:date` takes `requestId`, current `version`, the full `rows` array and optional `rowOrder`. It returns the saved schedule. The date is a strict Taipei calendar date.
- GET `/api/dot-progress/schedule/:date/history?offset=0` returns retained before/after snapshots with `history`, `total`, `limit`, `offset`, and `nextOffset`.
- GET `/api/dot-progress/schedule/:date/recovery-preview?revision=N` reads one explicitly selected historical revision and compares its inserted rows with the current board and every subsequent revision. It returns the source version, actor/time, exact added IDs, eligible rows, protected rows and later field changes without writing.
- POST `/api/dot-progress/schedule/:date/recovery` accepts `requestId`, current `version`, `sourceRevision` and a nonempty, unique `removeIds` list of at most 50 owner-selected eligible IDs. It rechecks eligibility under transaction locks, removes only those independent saved rows and saves a new retained schedule revision. All other current rows and the full current `rowOrder` are preserved.

Each planned row has `id`, nullable existing `projectId`, required safe `projectLabel` (160 characters) and explicit `goal` (4000), `plannedStart`, `plannedEnd`, `status` (`planned`, `active`, `waiting`, `done`) and `actualIds`, plus optional boolean `archived` and the daily `repeat` rule described above. Only `archived:true` is retained; false/absent have the legacy unarchived canonical shape. A new archived row is rejected, and an archive/unarchive transition must preserve every other row field. Planned timestamps are both null or both known ISO timestamps with timezone; a known span is chronological, at most seven days and overlaps the selected Taipei date. At most 50 rows and 500 total actual references are accepted. Row IDs are unique and an actual record belongs to at most one planned row. Referenced projects and actual records must exist. Text uses the existing private-text safety validation; the existing 256 KiB request-body ceiling also applies.

`rowOrder` contains at most 550 unique valid IDs for supplied saved plans or existing actual records used as derived-group IDs. A newly supplied order is validated without creating row metadata. An omitted order preserves the existing order exactly and stays absent from the request receipt payload for legacy compatibility; explicit `[]` clears ordering. An old client may remove a plan while preserving its old order ID; clients ignore unresolved IDs rather than inventing rows or pruning metadata.

Per-actor request receipts preserve the original successful reply across later edits and restart. Reusing an ID with changed content or sending a stale version returns 409. Rows, revisions and receipts commit atomically under a dedicated schedule lock with the existing transaction pattern; first writes to an absent board serialize as well. The schema adds only independent schedule tables and their display-order column, preserving actual work tables. Protected non-production debug metadata extends the existing diagnostic route, while production remains concealed.

## Validation

Synthetic PostgreSQL and fresh Chrome regression coverage exercises version races, rollback/restart, deduplication, unchanged actual records, dragging, resizing, ordering, Undo, failed/uncertain saving, conflicts, cancellation, logout/revalidation, browser return and 390/desktop layouts. Production checks use anonymous contexts and compare released assets, privacy boundaries and the unchanged completed-result projection. Real administrator acceptance can use the owner's existing normal browser session without credential extraction.

## Earlier ordering revision and recovery

The initial workspace release incorrectly promoted all explicit-goal derived groups into unscheduled saved rows when reordering. That wrote independent schedule rows/revisions only; it did not edit actual timeline, project or push tables. The corrected interface does not automatically change previously saved data, because an intentionally unscheduled plan is indistinguishable from such a promoted row without checking its revision history.

In the owner's normal administrator session, open the collapsed schedule history. It loads only on request and pages through retained versions, showing the version, actor, Taipei timestamp and row differences by ID. Review the historical ordering revision's added IDs and field-level before/after values. Select that revision explicitly to request a read-only recovery preview; the interface does not infer a source revision from a timestamp or choose any row automatically.

A possible derived row must be new in that source revision, have planned status and no planned interval, use the first referenced actual record as its stable ID, and match the explicit project/goal of every referenced actual record at the source time. Every referenced interval or known-endpoint milestone must overlap the selected Taipei date using the same half-open date rule as the actual timeline. Its current row must remain unchanged. Any later content change, including a change subsequently restored, archive transition, removal/recreation or actual-record version change, protects the row. Changing array position alone is not a content change. The source-time match establishes provenance, not the intent of the old operation: legacy schedule revisions do not identify whether an unscheduled plan was intentional. The owner must verify the selected source and rows.

The server checks the complete contiguous sequence through the current schedule version, including consistent before/after transitions. Missing, malformed or more than 1000 subsequent revisions fail closed rather than declaring truncated history safe. Actual snapshots are selected using database timestamps and checked against current data and versions. The current actual update timestamp must also precede or equal the source revision timestamp, preventing a waiting transaction's earlier start timestamp from treating a later update as an unchanged source snapshot. A preview uses a single repeatable-read snapshot. Applying recovery locks actual and schedule mutations, checks an exact idempotent receipt first, then recomputes eligibility and rejects the entire request if the current version or any selected ID is invalid. It never accepts client-supplied replacement rows or eligibility claims.

Both source confirmation and eligible-row checkboxes start unchecked; protected rows cannot be selected. A newer save invalidates the preview and requires an explicit reread. Applying a confirmed subset removes only those saved plan rows; the same actual groups become their original unsaved derived view, while actual intervals/details, unrelated plans and archived QA plans remain intact. Retained schedule history records the actor and complete before/after snapshots. The original request receipt remains immutable across retries, later edits and restart, and its operation namespace cannot collide with an ordinary save.

Undo submits the recovery's full before snapshot and display order with the current version and a fresh ordinary save request, creating another retained revision. Never delete revisions, receipt rows or actual work to repair display metadata. Publishing this interface performs no production repair or automatic cleanup. Only the owner uses the existing authenticated UI to compare real records and explicitly apply a reviewed subset.
