## Problem (Hank 2026-06-01 19:31 TW)

「任務卡狀態編輯 UX 問題 — 無法將子卡移動到特定某個狀態，只能透過點擊按鈕來移動到下一個預設的狀態，導致我無法將子卡移到特定狀態，也無法將子卡移除，需要有移除的選項，被移除的子卡也會被歸類到歷史紀錄供查看」

具體三個痛點:

### Pain 1: 無法選擇任意目標狀態
目前看板 UI 的「move」按鈕設計成 next-default-status linear flow (backlog → todo → in_progress → review → done)，但實際工作中:
- 想把卡片從 `review` 退回 `in_progress` (review 沒過要返工) → 點按鈕只會推進到 `done`
- 想把 `in_progress` 卡標 `blocked` (等別人) → linear flow 不接 `blocked` 分支
- 想把 `done` 卡 reopen 到 `todo` → 完全沒路徑
- Sub-card (auto-spawned children) 同樣只有 linear flow

### Pain 2: 沒有移除選項
任何卡片現狀都不能用戶手動移除。POST /api/mission/card/:id/archive (DELETE) 存在，但 UI 沒提供入口。Hank 想要 trash 動作 — 既不是「move to done」(那是完成)，也不是「permanent delete」(資料丟失)，而是 archive。

### Pain 3: 歷史紀錄查無
即使後端有 `/api/mission/cards/archived` 列出 archived cards，UI 沒有 history view 入口。Hank 看不到自己刪過的卡。

## Current state inventory

### Status enum (`backend/public/shared/kanban-status.js`)
```js
STATUSES = ['backlog', 'todo', 'in_progress', 'review', 'done', 'blocked']
```
6 個 status — `done` 是終態 (move 受限)、`blocked` 是分支態。

### Existing API
- `POST /api/mission/card/:id/move {newStatus}` — already accepts arbitrary target status (verified backend/kanban.js)
- `DELETE /api/mission/card/:id` — archive (sets `archived=true`)
- `POST /api/mission/card/:id/restore` — un-archive back to backlog
- `GET /api/mission/cards/archived?page=N&limit=20` — paginated history

**Backend 已經支援任意狀態移動**！痛點純粹是 UI 沒暴露這些功能。

### Existing kanban view files
- `backend/public/portal/kanban.html` — main kanban board
- Sub-cards rendered as children inside parent cards (need to find render code)

## Design

### Solution 1: Status picker (replace next-default button)

替換「move to next status」按鈕為 **status picker dropdown/popover**:

```
[ 🔄 In Progress ▾ ]
   ↓ on click
┌─────────────────┐
│ 📦 Backlog      │
│ 📋 TODO         │
│ ✅ Done         │
│ 🚫 Blocked      │
│ 👀 Review       │  ← grey out current
│ ─────────────── │
│ 🗑️ Archive (move to history) │
└─────────────────┘
```

行為:
- 點 status chip 即時呼叫 `/api/mission/card/:id/move` 帶 chosen status
- 灰底 disabled = 目前 status (`backlog` row 灰底表示卡在 backlog)
- mobile (390x844): chip popover 改成 bottom sheet (full-width)
- desktop (1280x800): chip popover at button anchor

### Solution 2: Archive action

Status picker 底部加 separator + `🗑️ 移到歷史紀錄`:
- 點擊 → confirm modal「移到歷史紀錄? (可從 History 還原)」
- Confirm → `DELETE /api/mission/card/:id`
- 卡片從看板列消失，加入 archived 清單
- Toast: 「已移到歷史紀錄 — 還原」(undo button calls `/restore`)

### Solution 3: History view entry

Kanban header 加 history 按鈕:

```
[Kanban Board]  [+ New Card]  [⚙️]  [🕓 History]
```

點擊 → 新 panel/drawer 顯示 archived cards:
- 分頁 (existing `?page=N&limit=20`)
- 每張卡顯示 title / 上次 status / archived 時間 / `[↻ Restore]` button
- Restore → `/restore` → 卡片回到 backlog + toast「已還原至 Backlog」
- mobile: full-screen overlay; desktop: 右側 drawer ~400px wide

## Open Questions for #6 (UI/UX)

1. **Picker shape**: dropdown (anchored popover) vs full bottom-sheet on mobile vs unified bottom-sheet 兩端皆用？提案 mobile=bottom-sheet, desktop=anchored popover (Material/Apple HIG common pattern)。
2. **Archive 入口位置**: 在 status picker 內(內聚 menu) vs 卡片右上角獨立 `⋯` menu(顯眼但增加 UI 點)？提案 picker 內 + separator 區隔 (不增 UI 點)。
3. **Confirm modal 用法**: archive 該不該 confirm？刪除類動作通常要 confirm，但有 toast undo 可能就夠了。提案 confirm + toast 雙保險 (per memory feedback_rendering_cards_screenshot_review 對 destructive 強調 confirm)。
4. **子卡是否區別對待**: sub-card 跟普通卡同行為 vs sub-card 不可手動 archive (只能等 done retention TTL)？提案統一行為 (簡化)。
5. **History 入口形式**: header 按鈕 vs settings drawer 內子 menu？提案 header 按鈕 (顯眼，single click)。
6. **Restore 目標 status**: 永遠回 backlog vs 回到 archived 前的 status？目前 `/restore` 已是 backlog，是否要改？提案維持 backlog (符合「重新規劃」語意)。

- 不改 backend API
- 不做 drag-and-drop card-to-status (touch+drag UX 複雜，picker 更精確)
