The Timehut page (`/AiHankApps/hub/#app-timehut`) mounts `hub-qa.js`. GIFs are fetched only after pressing Play. Every review/API/media byte uses the existing administrator gate and private/no-store headers. Original GIFs are stored in the existing private R2 bucket under `aihankapps-hub/qa/`, outside the public Git repository and outside the device-file expiration table. Only an operator over the existing Railway deployment channel may upload media or publish snapshots/results. SHA-256 and GIF signature checks verify these newly uploaded review assets, not pCloud backups.

Routes, also discoverable in `/api/help`'s existing hub category:

- `GET /api/aihankapps/hub/qa/timehut?after=0`: selected/default snapshot, append-only comments after this global ID (500/page), results, `nextCursor`, `hasMore`. Optional `batch=timehut-batch02` selects a batch and filters comments/results. **Without `batch`, comments paginate across ALL batches**, including archived history; results identify their batch. Never returns object-storage keys or capability URLs.
- `GET /api/aihankapps/hub/qa/timehut/media/01?batch=timehut-batch02`: that batch's original GIF, proxied with administrator authentication. Omitted batch always means legacy01, even when a newer batch is active.
- `POST /api/aihankapps/hub/qa/timehut/comments`: `{requestId: UUID, batch?, item: "01", revision, decision: "comment"|"changes"|"approve", body}`. Administrator and exact same-origin required. The request UUID remains globally unique and bound to its batch: an exact retry returns the original row; different content or cross-batch reuse is 409. Stale revisions are 409; drafts remain in the page module across rerenders. No HTTP update/delete/import endpoints exist.
- `GET /api/debug/aihankapps-hub-qa` is available only outside production or in the debug environment, with the same administrator gate. Production operator reads supply the corresponding audit state.

Own tables: `aihankapps_hub_qa_batches`, `aihankapps_hub_qa_comments`, `aihankapps_hub_qa_results`. No product/account/photo tables are modified. Comments and operator responses are append-only. Results reference an existing batch/item and optional exact comment ID in that same batch/item. A stable `result_key` remains globally unique, bound to the batch: exact retries are idempotent; changed responses or cross-batch reuse reject with `QA_RESULT_CONFLICT`. Do not reuse keys in a later batch. Snapshot publication verifies all ten media originals. Existing comments retain their original batch/revision even after a new active snapshot is published.

Batch IDs are bounded strings matching `/^timehut-batch[0-9]{2,6}$/` with a positive numeric suffix; `timehut-batch01` is the legacy batch. Zero, one-digit suffixes, more than six digits, nonstrings and path-like values are invalid. Preserve the exact ID spelling everywhere.

Uploads JSON: ten `{batch?,item,path,sha256,size}` entries with distinct items 01–10. Use the intended batch on every entry for new reviews. Only an absent `batch` defaults to `timehut-batch01`; explicit null/empty/invalid values reject before any upload. The bridge passes each entry's batch to `prepareMedia({batch,item,sha256,size})`; the backend derives `mediaKey(item,sha256,batch=legacy)` under `aihankapps-hub/qa/timehut/<batch>/`. Receipts include batch/item/hash/bytes/uploaded, never storage capabilities. Do not re-upload archived originals; publication retries do not authorize changing stored originals.

Batch JSON: `{id: "timehut-batch02", app: "timehut", reviewState: "active", ...}` with ten items `{id,revision,sha256,bytes,mediaKey,title,before,after,status,releaseStatus}`, current platform coverage and limitations. `publish` forwards this exact payload, including its `id`; it never selects or rewrites a batch ID. Results JSON: `{batch?,key,item,commentId?,body}`; omission retains legacy01 compatibility. New results require that batch and item to exist; a supplied comment must belong to that same batch/item. Results can append processing notes to archived history without altering its frozen snapshot.

`read AFTER_ID [BATCH_ID]` forwards an optional selection to `read(pool,{after,batch?})`. `read 0` retains the old envelope with no batch property and works with the current single-batch deployment. After the multibatch backend is deployed, unfiltered reads cover every batch. A selected read's cursor is for that filtered view: never copy it into the global feedback checkpoint or mix selected and unfiltered cursors. The CLI returns one page; keep reading `nextCursor` while `hasMore` is true. `updates` always paginates the unfiltered feed, regardless of any display batch in a checkpoint.

Signed PUT capabilities exist only in the operator bridge's memory until upload completes. Never redirect raw `prepare-media` output to files, print it, place it in a checkpoint, or expose it to the browser. Use only the final upload receipts for evidence. Database/R2 credentials stay in the service's existing runtime configuration; operator commands neither export nor print them.

## Batch lifecycle, migration and deployment order

At most one batch may be active. Publishing a new active batch while another is active rejects with `QA_ACTIVE_BATCH_CONFLICT`; there is **no silent archive**. Explicitly publish the current full snapshot unchanged except for `reviewState: "archived"` first, preserving all items, revisions, original media references, metadata, coverage and limitations. Use the original private operator payload: browser/read projections omit `mediaKey` and cannot serve as publication originals. Keep concurrent operator changes coordinated; do not replace newer snapshots with stale copies.

Replacing an active item's media requires a new revision. Publication rejects the same batch/item/revision with different SHA-256, byte count or media reference as `QA_REVISION_CONFLICT`, under the same transaction lock used by comments. Existing feedback stays attached to its original revision; an old form cannot approve the replacement.

Once archived, all review items, revisions, original media and other review metadata are frozen; reactivation rejects with `QA_BATCH_ARCHIVED`. Exact retries are idempotent. The four E2E journal fields `coverage`, `coverageNote`, `phaseSummary` and `updatedAt` may still advance through the verified operator publisher, returning `progressOnly: true`. This keeps hourly coverage updates working when the latest review has completed and there is no new ten-item batch. These updates cannot alter any original item, reopen forms or replace history. Do not rebuild archived legacy01 from the active batch. Start the next numbered batch with its own originals and decisions. Comments/results remain append-only and batch-linked; archival removes pending forms, not history or evidence.

Migration adds `batch TEXT NOT NULL DEFAULT 'timehut-batch01'` to existing result rows, retaining their IDs, keys, bodies, comment links and timestamps. Existing batch01 snapshot/media/comments remain unchanged. Preserve the existing global unique constraint on comment request UUIDs and result keys; do not drop it or replace it with per-batch uniqueness. The backend performs the migration through its normal guarded preparation; this document does not authorize a separate production database write.

## Completed batches and direct alert replies (2026-11-22)

Hank replied directly to `human-timehut-qa-review-next58-r1`: the items were already handled; move to the next stage and remove the old items. He normally replies on alerts. Therefore the hourly entry point is `node tools/aihankapps-hub/qa.js updates /PRIVATE/CHECKPOINT.json`, which reads the review-alert family's current state and **all retained confirmations, including old cleared warnings**, before paginating item comments. A plain confirmation has no approval meaning. Responses are deduplicated by alert ID plus ack/plan timestamps and content signature; interrupted `IN_PROGRESS` operations are returned for resumption. The reader never advances handled cursors. Save private raw results, act, reply with a note beginning 已讀到對策：, then mark the exact observed response handled.

The general alert snapshot limits acknowledgements by their first `acked_at` (60 days, 500 rows). Updating a plan moves `plan_at`, not that first acknowledgement time, so that snapshot alone can miss a late reply on an old closed review. The QA operator supplements it through the existing container bridge with `{action: "alert-replies", after: "", limit: 100}`, forwarded to `qa.alertReplies(pool,{after,limit})`. This action is operator-only, with no HTTP route, schema initialization or production data writes. Explicit null/zero arguments remain explicit for backend validation; only omitted arguments receive defaults.

`alert-replies` returns `{success:true,acks:[{id,at,planAt,plan,title,triage,answered}],nextCursor,hasMore}` for the entire `human-timehut-qa-review-` family, without an age cutoff. `nextCursor` is an alert reference, separate from numeric comment cursors. The backend accepts 1–500 rows per page; the bridge requests 100 so long UTF-8 plans and triage notes fit the shared Railway transport's stdout buffer. It reads every page to exhaustion; there is no total 500-row truncation. Each invocation starts from the empty reference so a changed plan on any previously visited reference is found again. References are paginated lexicographically by the backend; a stalled/repeated cursor or malformed page aborts the read. Edits made after a row was read are observed on the next scan. This is the latest retained state, not an event log of intermediate edits already overwritten or deleted before polling.

After a complete scan, supplemental facts replace this family's snapshot acknowledgement facts while current active warning entries and unrelated snapshot data remain. New plan/timestamp/triage/answered values take precedence; a removed acknowledgement cannot be resurrected by an older warning's embedded ack. `updates` includes `alertReplySource: {mode:"timehut-paginated",complete:true,pages}`. If and only if the deployment rejects the action with `QA_ACTION`, it retains legacy snapshot behavior and reports `{mode:"legacy-alerts",complete:false,reason:"QA_ACTION"}`. That fallback cannot certify coverage of old late replies. Database/transport errors, malformed pages and interrupted pagination propagate instead of returning a partial successful scan. Treat incomplete coverage as a rollout limitation, not proof that no reply exists. The scanner does not mark replies handled or advance input checkpoints.

Deploy the backend `alertReplies` implementation and the matching container action before relying on complete history coverage from the updated local bridge. No shared alert reader, automation definition, schedule or checkpoint format is changed.

Operator snapshots accept `reviewState: "active" | "archived"` and bounded `phaseSummary`. Archived batches retain the original ten items/media/comments/results. Their active GIF cards and forms disappear; a collapsed completed-history section remains, with no submission controls. The page shows the next E2E phase and actual coverage. A stale open form receives 409 `QA_BATCH_ARCHIVED`; existing exact idempotent retries retain their prior receipt. The insertion statement also checks archive state atomically. Archiving does not exclude any original E2E denominator, imply 100% coverage, or delete evidence. New product UI is reviewed only after a new numbered batch is ready.
